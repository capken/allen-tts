# allen-tts

把文字合成为语音。底层是 allen-tts 命令行工具，它已经把三家服务商的参数差异抹平，
所以这里只需要决定「调什么」和「出错了怎么办」。

## 第一步：永远先探测状态

执行本技能目录下的 `scripts/preflight.sh`，读取它输出的 JSON。

这一步不能跳过，也不要用别的方式猜测环境状态——它一次就把是否安装、密钥是否就绪、
默认音色是否设好全部查清，避免来回试探。

然后按 `ready` 字段分支：

- `ready` 为 true → 直接合成，见下面「合成」一节。
- `ready` 为 false → 读 `references/setup.md`，按 `missing` 数组**从前往后**补齐。
  数组是有序的，前面的没做完后面的做不了。

## missing 各值的含义

| 值 | 含义 | 去哪处理 |
|---|---|---|
| `binary` | 命令行工具没安装 | setup.md 第 1 步 |
| `cli_too_old` | 已装的版本低于本技能要求 | setup.md 第 1 步，重跑安装命令升级 |
| `default_provider` | 没有确定默认服务商 | setup.md 第 2 步 |
| `api_key` | 默认服务商没有可用密钥 | setup.md 第 3 步 |
| `default_voice` | 没有设默认音色 | setup.md 第 4 步 |

## 合成

动手前先读 `references/usage.md`——只在真要合成时读，光是配置环境不需要它。

基本形式：

```
allen-tts speak -p <服务商> -v @default --json "<文本>" -o <输出路径>
```

三条必守的规则：

1. **总是加 `--json`**，然后从标准输出的 JSON 里读 `output` 字段（绝对路径），
   不要自己猜文件在哪。
2. **`warnings` 非空时必须转述给用户。** 它表示某些设置被裁剪或丢弃了，
   瞒着用户等于让他们以为参数生效了。
3. **出错时读 `references/troubleshooting.md`**，按 `error.code` 和 `error.retryable` 决定
   是重试、换服务商还是改参数。不要盲目重试。

完成后把音频文件的路径告诉用户。

## 有新版本时

preflight 输出里 `update_available` 为 true 时：**先把用户当前要的事做完**，
然后用一句话提一下有新版本，附上 `release_notes` 链接，问要不要更新。

不要打断正在进行的任务，不要反复提醒，更不要自动更新——更新意味着往用户机器里写入
会被后续会话自动加载的新指令，必须由用户明确同意。用户同意后按 setup.md 的「更新」一节做。

## 用户要改配置时只改那一处

已经配好之后，用户常会提局部调整。不要因此把整个引导重跑一遍：

- 「换个音色」「换成女声」→ 只做 setup.md 第 4 步。
- 「换成 fish / 用 Cartesia」→ 做第 2 步，确认那家的密钥（第 3 步），再做第 4 步。
- 「这次慢一点 / 高兴一点」→ 这不是改配置，是本次合成的参数，直接加到命令里。

## 硬约束

- **绝不把 API 密钥写进任何文件，也不在回复里回显密钥。** 密钥只通过环境变量提供；
  配置文件里只保留 `${ENV}` 形式的引用。用户若把密钥贴进了对话，不要复述它，
  引导他们写进自己的 shell 配置。
- **需要提权才能写的目录，先问用户。** 不要擅自使用 sudo。
- 修改用户配置只通过 `scripts/configure.sh`，不要手工改写 YAML——那个脚本是幂等的，
  且会保留用户自己添加的其他音色别名。
